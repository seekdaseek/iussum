# FEEDBACK: friction hit in x402, MWA / Seed Vault and the Subscriptions & Allowances program

Every item was hit while building iussum (2026-10-19). Each has a reproduction that exists in this repo. "Observed" means I saw it; "inferred" means I did not isolate the cause.

## x402 (`@x402/*` 2.28.0, facilitators payai and x402.org)

1. **payai validates every extension key as `{ info, schema? }`.** A flat `extensions.iussum = { mandate, ... }` is refused: `Extension 'iussum' missing required 'info' property`. x402.org passed the flat form to simulation. Repro: `FAC_URL=https://facilitator.payai.network EXT=1 node probes/g02-real.mjs` (EXT=2 wraps in `info` and passes). Source of the shape: the same convention x402 uses for its own extensions; the requirement is not stated where a third-party extension author would read first.
2. **`onBeforeVerify` abort answers 402, not 403.** A seller that wants to tell an agent "this payment is outside your mandate" cannot do it from the documented hook: the abort path of `paymentMiddleware` returns a 402 payment-error (`node_modules/@x402/express/dist/cjs/index.js:236-247`). iussum mounts its own middleware ahead of `paymentMiddleware` for the 403. Repro: `packages/seller/test/gate.test.js`, "amount over per_payment_max answers 403".
3. **No hook to add a header after settlement.** The receipt has to go back with the 200, after x402 has settled. `paymentMiddleware` buffers `res.writeHead`, sets `PAYMENT-RESPONSE`, then replays the buffered calls. iussum wraps `res.writeHead` *before* x402 binds it and reads `payment-response` there (`packages/seller/src/gate.js`). It works because of an implementation detail (the order of `bind`), not a contract.
4. **The stock SVM client pays only from the signer's own token account.** A delegate flow (the agent pays out of the principal's account as the SPL delegate) needs a custom `SchemeNetworkClient`; `createPaymentPayload` hard-codes the source ATA from `signer.address`. Repro: compare `@x402/svm` `exact/client/index.js` (the `findAssociatedTokenPda({ owner: this.signer.address })` call) with `packages/agent/src/agent.js`.
5. **Client spend controls reject a custom scheme.** `All payment requirements were rejected by spendControls: only default assets or entries in spendControls.allowedAssets are allowed`, because a custom scheme has no `findDefaultAsset`. Repro: first run of `probes/g04-live.mjs` before `client.setSpendControls(false)`.
6. **The smart-wallet allow-list is invisible and excludes the Subscriptions program.** `GET /supported` on x402.org shows `features.smartWalletSupported: true` but not which programs are allowed; both live facilitators refused a Subscriptions pull with `invalid_exact_svm_smart_wallet_program_not_allowed: De1egAFM…`. Repro: `STAGE=b NONCE=0 FAC=<facilitator> node probes/g04-live.mjs` (see `docs/ALLOWANCE.md`, source read at `@x402/svm` `exact/facilitator/index.js:782-796`, `:1305`, `:1323`).
7. **payai's deployed verify differs from the 2.28.0 package.** A 100,000 compute-unit limit that the installed library accepts locally was refused by payai with `invalid_exact_svm_payload_transaction_instructions_compute_limit_instruction`; 30,000 and 40,000 reached the program check. Inferred: version or config drift on their side. Repro: `CU=100000 STAGE=b FAC=https://facilitator.payai.network SKIP_GRANT=1 node probes/g04-live.mjs`.
8. **The 402 refusal reason is only in the `PAYMENT-REQUIRED` header.** The body is `{}`. A client that wants to show why a payment was refused has to base64-decode the header (`g02-real.mjs` does).

## MWA and Seed Vault (Seeker, Android 16, wallet app on the device)

1. **A sign request on a chain the wallet is not set to ends in `CancellationException` with no explanation.** `authorize({ chain: 'solana:devnet' })` succeeded, then `signAndSendTransactions` was cancelled with `SolanaMobileWalletAdapterError: java.util.concurrent.CancellationException`; the wallet's Network setting was Mainnet. It worked after switching the wallet's setting to Devnet (inferred as the cause, not isolated). Repro: `apps/seeker-probe` button T1 with the wallet on Mainnet.
2. **`signMessages` and Sign-In-With-Solana text are never shown.** The Verify sheet shows a "Message" skeleton for about 0.3 to 1 s and then only "Confirm that you are authorized to sign transactions with this wallet." The Sign in sheet shows "Continue with DAPP" and the application, no statement, nonce or expiry. Repro: `apps/seeker-probe` buttons T3 and T2; recordings in `docs/seedvault/`.
3. **A transaction sheet shows the mint and the amount, not the delegate and not the memo.** For `ApproveChecked` it shows `4zMM…ncDU`, `2.5` marked red, the fee, and "Approving this transaction will allow a third party to spend your asset in the future." Repro: T1 (`5gUy9rev…`).
4. **Seed Vault appends ComputeBudget instructions.** The signed T1 had two extra instructions and a 45,000-lamport fee, so any "exactly these instructions" check has to allow ComputeBudget (iussum's grant check does). Repro: `getTransaction 5gUy9revfEvxKpsnjJ2rR2WnrL13LMrHPaeMweQBU1kxn1m2WQAFRvmZ4CPY2ExJsGuTBVEEG4HkrBCwzE61PF8i`, `test/vectors/recorded/grant-T1-5gUy9rev.json`.
5. **An "I trust this site" toggle gates Approve for an unrecognised domain.** Every transaction from `ochinimus.app` (debug-signed probe) showed a domain warning and a disabled Approve until the toggle was on. Whether a release-signed app with a matching Digital Asset Links file removes it is UNTESTED.
6. **The info icon next to "Message" is on screen for about 0.3 s**, too short to tap by hand or by a polling script; three attempts failed (`docs/SEED-VAULT.md`). Its text is unknown.
7. **`signMessages` returned a 64-byte detached signature**, not message plus signature; the first probe assumed the latter and its `returned_starts_with_message` flag read false by design. Repro: `apps/seeker-probe` T3, then `probes/verify-seedvault.mjs`.

## Solana Subscriptions & Allowances program (`De1egAFM…`, `@solana/subscriptions` 0.5.0)

1. **`x402-wallet`'s hand-written builders are stale against the IDL.** `initSubscriptionAuthority` and `createFixedDelegation` take a `payer` account the builders omit; `revokeDelegation` takes two accounts, not four (`idl/subscriptions.json` of solana-foundation/subscriptions at 56de552 versus `x402-wallet/src/allowance.js`). Not hit at runtime because nuntius uses the generated client. Repro: `docs/ALLOWANCE.md`.
2. **One delegate per token account.** The program's Subscription Authority takes the single SPL delegate slot, so an agent's `ApproveChecked` and a Subscriptions grant displace each other (localnet, both directions, `probes/g04-local-results.json`). The design has to pick one path per token account.
3. **A fixed delegation has a total, not a per-payment cap.** Only the recurring variant has a period; neither has a per-payment maximum. That is why Phase 1 enforces `per_payment_max` and the period budget in the seller and agent checks and uses the on-chain amount only as the loss ceiling.
4. **A pull needs more than 20,000 compute units.** With a memo the pull ran out of compute at 20,000 (`ProgramFailedToComplete` at instruction index 3) and passed at 100,000, which collides with the static x402 limits. Repro: `probes/g04-local-facilitator.mjs`.
5. **A detail that changes the design:** the facilitator reports the Subscription Authority PDA as `payer`, not the delegatee or the owner, so any "payer == agent" check has to be redefined for that path (`docs/ALLOWANCE.md`).

## Added in Phase 1.1 (found while fixing the gate review)

**x402**
9. **`resource.url` is declared by the seller, and the client has nothing to compare it with.** The 402 carries `resource.url`, and `onBeforePaymentCreation` only sees that value. An agent that matches its mandate against it can be told "this is an allowed URL" while the request went elsewhere. iussum's agent remembers the URL it actually asked for and refuses on a difference. Repro: `test/phase11/fixes.test.js`, "a seller that DECLARES an allowed resource.url while the agent asked for another URL".
10. **A seller that derives its resource from the `Host` header can be told what to sign.** Express exposes `req.get('host')`, and a client chooses it. `createSellerGate` now requires a configured canonical `origin`. Repro: `test/regression/f5-host-header.test.js` (Node's `fetch` ignores a `Host` override, so the test uses raw `http.request`).

**Solana RPC (public devnet)**
1. **`getSignaturesForAddress` with `until` or `before` set to a signature confirmed a moment ago fails with `Transaction <sig> not found` for one to a few seconds.** The node answering has not indexed it yet, although `getSignatureStatuses` and `getTransaction` already return it. Found by the devnet demo (a fresh grant failed its own "is it current" check in 6 of 10 scenarios), invisible to the fake chain in the unit tests. iussum retries exactly this error for up to about 7 seconds (`makeRpc` in `packages/core/src/chain.js`, test `makeRpc retries the "Transaction <sig> not found" index-lag error`). Repro: `node probes/repro-until-lag.mjs` (sends one memo transaction from the throw-away principal and asks for signatures newer than it, printing each second).
2. **Bursts of `getTransaction` calls are rate limited (HTTP 429)** on the public devnet RPC: the first Phase 1 demo run failed this way while the resolver walked 50 transactions. iussum now retries 429 and 5xx with jittered backoff up to 8 times and pages with a bounded number of calls; a heavier client should use a keyed RPC.
