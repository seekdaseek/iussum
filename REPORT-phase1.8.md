# REPORT: iussum Phase 1.8 (2026-10-21)

Baseline for the new regression tests: **`f62ae84`**, the public HEAD at the end of Phase 1.7. This pass answers Addendum N, the seventh review of `c521b31..f62ae84`. Every repro script of the review (`review-20261021g/`, gitignored) was run against `f62ae84` first and again after the fixes: [docs/phase18/repro-before-f62ae84.txt](docs/phase18/repro-before-f62ae84.txt) and [docs/phase18/repro-after-fix.txt](docs/phase18/repro-after-fix.txt). Normal pushes only; devnet and localnet only; nothing on the VPS; nothing was posted anywhere.

The review's headline finding was right and old: **N1 is a defect from before Phase 1.6** (it is the same at `142276f`): the agent trusted the transaction signature that the SELLER puts in `payment-response`, so a seller could lift the period budget by repeating a signature. It is fixed, with a property-test generator in which a seller repeats a signature.

## Still UNTESTED

Moved out by this pass: a seller that repeats a signature (the live path, a restart and a kept payload, plus the property generator); a superseder without a slot at the gate, the resolver and the core; a warm grant during an attack; a close during a paid request; an abort before the lock; the rollback direction of the lock with the real `142276f` code (`a2`, two processes); the independent verdict_id recomputation as a regression; the whole suite as root.

- **Root was tested in a Linux arm64 container** (`node:24-bookworm` on Docker Desktop), not on native root on macOS and not on x86 CI. The suite found one root-sensitive test in the previous pass; whether another exists on a different file system is not shown.
- **The rollback guard is per directory, not per grant.** Two new agents of different grants in one directory but different processes share `agent.lock`; the first creator's exit removes it, which ends the rollback guard for the other. In one process the file lives until the last agent of the directory is closed. Tested in one process only.
- **An unknown grant is now 503, never 403.** A seller's node cannot tell a grant that does not exist from one it does not show yet. The agent's bounded `Retry-After` retries cover the lag; a request with a made-up `grant_tx` costs the gate one read and a 5 s memo, and gets 503 for as long as it keeps asking. Not measured against a real lagging node.
- **The lanes are tested against fakes** (a node whose pages take a configured time), not against a public node with an attacker's long history. The caps (4 cold, 2 warm, 64 queued) are defaults, not measurements.
- **`close({ timeoutMs })` keeps the lock on timeout and does not release it when the payment returns later**; only process exit (or a second `close()`) does. A deployment that wants to restart in place after a timeout restarts the process.
- **The p2 fairness is by order of arrival** (a promise chain in front of the bucket); a waiter that never gets its tokens (a rate that fell to the floor) holds the queue, which is what the floor and the stall time are for.
- **Carried over, unchanged:** one keyed provider, one afternoon (Phase 1.7); the mainnet public default is the devnet node's measured one by host name; the empty-page `before` case behind a load balancer; a real lagging history node on devnet; power loss for the directory fsync; the legacy `agent.lock` check treats our own pid as stale; held reservations count against the current period whatever period they were reserved in; `verdict_id` is a reference, not a signature; a wSOL account and a Token-2022 grant on chain; the Seeker-signed grant (Phase 2); third-party sellers; anything on mainnet; the period budget is not enforced on chain, only `total_cap` is (scenarios 16 and 16b).
- **Said plainly about process:** the first full `npm test` of this pass hung for more than ten minutes, and a later container run as root hung the same way. The cause is now known: when a test fails, the servers it started are not closed, the test process then never exits, and `npm test` had no per-test timeout, so a failure looked like a hang. Two tests of mine were timing-dependent (they closed the agent after a fixed `sleep` and failed under CPU load): the close during a paid request and the close with a timeout. They now wait until the paid request is really in flight. `npm test` now runs with `--test-force-exit --test-timeout=300000`, so a failure is a failure. Six busy loops in a root container, three repetitions of the phase15 to phase18 files: no failure. Two leftovers disclosed earlier stay in the public history by decision (the treasury-address prefix in two commits of `REPORT-phase1.2.md`, one line about a payout-documentation check) and the `git add -A` of Phase 1.5 (`533e49b`); this pass named every path it added.
